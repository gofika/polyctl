# Instance login

How polyctl handles the logins of the instances it creates: Windows passwords and the SSH keys of Linux instances.

- [Linux: SSH keys only](#linux-ssh-keys-only)
- [Windows passwords](#windows-passwords)
- [Managing SSH keys](#managing-ssh-keys)
- [Access on AWS and Alibaba Cloud](#access-on-aws-and-alibaba-cloud)
- [Over SSH](#over-ssh)

`<tree>` below stands for `aws ec2 instance`, `gcp compute instance` or `aliyun ecs instance`. Platform details (default users, temporary access, required IAM / RAM actions) are on the platform pages: [AWS](platforms/aws.md), [Google Cloud](platforms/gcp.md), [Alibaba Cloud](platforms/aliyun.md).

## Linux: SSH keys only

Every Linux create (`<tree> create`, and `aliyun ecs instance ensure`) sends an SSH key, never a password; there are no password flags for Linux. A Linux create without a usable key is exit code 2 before anything is created. On AWS and Alibaba Cloud a terminal asks for a public key (from a file or typed in) instead.

## Windows passwords

A Windows instance logs in with a user name and a password. When polyctl creates one, it stores the login in `inventory.db` (table `instance_secrets`) so you can read it later:

```text
<tree> password <name|id>          # INSTANCE, USER, PASSWORD
<tree> password <name|id> -o json  # {"instance","id","user","password","platform","profile","location","updated_at"}
```

| Platform | User | Password | Fetch later |
| --- | --- | --- | --- |
| Alibaba Cloud | `Administrator` | generated by polyctl | `password` reads the local store only; for an instance polyctl did not create, reset it in the ECS console |
| Compute Engine | `--windows-user` (default `polyctl-admin`) | set through the guest agent | `password --reset` sets a new one, also on instances polyctl did not create |
| AWS EC2 | `Administrator` | generated by the instance, decrypted with the key pair | `password [--key-file <path>]` asks AWS again |

- **Interactive create** prints user and password once done: on stdout after the change report, or on stderr with `-o json` / `-o yaml`.
- **Non-interactive create** never prints the password; a note on stderr names the user and the `password` command.
- **Storage**: the password (and, on AWS, the private key polyctl created) is encrypted with a data key kept in the credential store under `/instance-secrets` (OS keyring, else `credentials.json`). Copying `inventory.db` to another machine without that entry, or deleting the entry, makes the stored passwords unreadable (exit code 1). The data key is created on first use only; while passwords are stored and a run cannot reach every backend (with `credential_store: auto` and no keyring, as in many SSH or cron sessions), a create that would store a password fails before the instance is created, instead of creating a second data key in `credentials.json`: run it where the keyring is available, or set `credential_store` to the store that holds the key. Passwords sealed by earlier releases with a second key in the other backend are still read. Deleting `inventory.db` loses them; no platform can show them again. A sync and `--refresh` leave them alone; `auth rename` moves them. `auth logout` keeps them but detaches them from the profile (with or without `--keep-inventory`): an account logged in later under the same profile name, which may be another account, does not see them in the `password` picker or by instance name. `password <instance id>` still shows them, with a warning that they were stored for the account that was logged out. A rename onto a name that still holds rows of such a logged-out account detaches those rows instead of merging them; a rename that was interrupted after moving the rows and is run again keeps the rows it moved.
- **Cannot store**: an interactive create prints the credentials with a warning that they cannot be shown again; a non-interactive one fails with exit code 1 and says how to set a new password (platform console, or `gcp compute instance password <id> --reset`).
- **Not ready yet** (AWS or Compute Engine password not available within `--password-timeout`, or `--no-wait`): the create still succeeds (exit code 0) with a note naming the command to run later.
- `password` on an instance with nothing stored is exit code 4.
- `--dry-run` generates no password, stores nothing and creates no key.
- Deleting an instance through polyctl removes its stored credentials. On AWS it also deletes the key pair polyctl created for it, never one of yours.
- Generated passwords are 20 characters: upper- and lower-case letters, digits and at least one of `@#-_+=.,:`, no quotes, spaces or look-alikes (`0 O 1 l I`).

## Managing SSH keys

`<tree> ssh-key list|add|remove` manages the public keys a Linux instance accepts.

```text
<tree> ssh-key list   <name|id> [--user <name>]
<tree> ssh-key add    <name|id> (--ssh-key <public key> | --ssh-key-file <path>) [--user <name>] [--dry-run]
<tree> ssh-key remove <name|id> (--fingerprint SHA256:... | --ssh-key <public key> | --ssh-key-file <path>) [--user <name>] [--yes] [--dry-run]
       # AWS and Alibaba Cloud also: [--address <ip>] [--port 22] [--identity-file <private key>] [--login-user <name>] [--accept-new-host-key]
       # location: --region (AWS, Alibaba Cloud) or --zone (Compute Engine)
```

Where the keys live:

- **Compute Engine** edits the instance's `ssh-keys` metadata through the API. No SSH login; the instance may be stopped. See [Google Cloud](platforms/gcp.md) for project-wide keys and OS Login.
- **AWS and Alibaba Cloud** edit `~/.ssh/authorized_keys` of the user, over SSH or a platform's temporary access. The instance must be running (otherwise exit code 1, with the `start` command to run).

Commands:

- **add** reads first. A key the user already has (same type and key data; comment and options ignored) is reported `unchanged` and nothing is written. When that line carries options that may stop the key from logging in to a shell (`command=`, `restrict`, `from=`, `expiry-time=`, such as the "Please login as ec2-user" line for root on AWS images), the detail names them and a warning goes to stderr; the exit code stays 0 and polyctl leaves the line as it is (a line appended after it would not help: sshd uses the first matching line). The change report names the key `key/<user>/<SHA256 fingerprint>`. Without a key flag, a terminal offers the `~/.ssh/*.pub` keys (one already on the instance is marked), another file, or typing the key; the non-interactive flow is exit code 2.
- **remove** removes every entry of the user that holds the key, in `~/.ssh/authorized_keys` and `~/.ssh/authorized_keys2` alike, and keeps the rest; `--fingerprint` is repeatable. A key that is not there is `unchanged`. Without a key flag, a terminal lists the keys for a multiple choice. It asks for confirmation (see [Confirmations](interactive.md#confirmations)). On AWS and Alibaba Cloud it refuses (exit code 1) to remove the key it logged in with, or the user's last key that sshd reads, so you are never locked out (keys in a file sshd does not read, such as all of `authorized_keys` when `AuthorizedKeysFile` names only `/etc/ssh/keys/%u`, can always be removed).
- **list** prints `USER`, `TYPE`, `FINGERPRINT` (SHA256), `COMMENT`, `SOURCE` (`authorized_keys`, `authorized_keys2`, `instance metadata`, `project metadata`). Marks: `in use` (the key the command logged in with), `read-only` (keys `remove` does not change, such as project-wide keys), `ignored` (keys the instance does not accept, such as an `authorized_keys2` that sshd is configured not to read), `restricted` (an authorized_keys line with `command=`, `restrict`, `from=` or `expiry-time=`). `-o json` / `-o yaml` fields: `user`, `type`, `fingerprint`, `comment`, `source`, `in_use`, `read_only`, `ignored`, `options` (the line's authorized_keys options), `restricted`.
- **`--dry-run`** reads (it may log in, or run the read-only listing through the platform's command) and reports `would create` / `would delete`; it never writes.
- **Windows** instances are refused with exit code 7; use `<tree> password`.

## Access on AWS and Alibaba Cloud

The key used to reach the instance is chosen in this order:

1. **`--identity-file`**: when given, the only key used.
2. **The local private key of the instance's key pair**: from the SSH agent, `~/.ssh/id_ed25519`, `id_ecdsa`, `id_rsa`, `~/.ssh/<key pair>.pem` or `~/.ssh/<key pair>`, when its public key matches the key pair. An encrypted file is matched through its `.pub` file; only the match asks for a passphrase (on a terminal; non-interactive: use an SSH agent). No other local key is tried.

   The SSH agent is the one `SSH_AUTH_SOCK` names. On Windows it may name a named pipe (`\\.\pipe\<name>`, also written `//./pipe/<name>`, as Pageant or another agent prints it); when it is not set, polyctl uses the Windows OpenSSH agent service (`\\.\pipe\openssh-ssh-agent`, which 1Password also serves), and says nothing when that service is not running.
3. **The platform's temporary access**, when there is no matching local key (no key pair, an unreadable one, or no private key on this machine) or the instance refuses it: on AWS Systems Manager Run Command, then EC2 Instance Connect; on Alibaba Cloud, Cloud Assistant. A one-time key is generated in memory; nothing is stored. See [AWS](platforms/aws.md) and [Alibaba Cloud](platforms/aliyun.md) for requirements and permissions.

The target user is `--user`, else the first default user that exists on the instance. A listing that may have been cut by the platform's output limit is refused with exit code 7.

When nothing works, the error names each way tried and why, and suggests `--identity-file`: exit code 3 when the platform denied every temporary way (missing IAM / RAM permission), exit code 1 otherwise.

## Over SSH

- **Address**: the public IP, else the private IP (with a note; you must reach the private network). `--address` and `--port` (default 22) override.
- **Login user**: `--login-user`, else the instance's default users tried in order (see the platform page); a note names the one used. When none works, the error lists each user and why.
- **Encrypted `--identity-file`**: asks for the passphrase on a terminal; non-interactive is exit code 2, use an SSH agent instead. Private keys are never stored or printed. Password authentication is never used.
- **Another user** (`--user`): edited through `sudo -n -u <user>`. A sudo that asks for a password or is not allowed is exit code 1 (log in as that user, or allow passwordless sudo). A user the instance does not have is exit code 4.
- **Host key**: checked against `~/.ssh/known_hosts` (and `/etc/ssh/ssh_known_hosts`). A changed or `@revoked` key is refused (exit code 1) and never replaced; run `ssh-keygen -R <host>` when the change is expected. An unknown host shows its SHA256 fingerprint and asks (default no; declining is exit code 0). The non-interactive flow needs `--accept-new-host-key`, else exit code 2. A trusted key is appended to `~/.ssh/known_hosts` (a dry run trusts it for that run only). `--yes` does not trust host keys.
- **The edit** creates `~/.ssh` (`0700`) and `authorized_keys` (`0600`) when missing, replaces the file atomically, keeps every other line byte for byte (comments, options, CRLF), refuses a symbolic link, and retries once when the file changed since it was read. SELinux contexts are restored.
- **Which files**: `add` writes `~/.ssh/authorized_keys`; `list` also shows `~/.ssh/authorized_keys2`, and `remove` deletes the key from both. The `AuthorizedKeysFile` sshd uses comes from `sshd -T` when it can run (as root), else from `/etc/ssh/sshd_config` and the files it `Include`s (the first setting outside a `Match` block), else OpenSSH's default `.ssh/authorized_keys .ssh/authorized_keys2`. A key in `authorized_keys2` counts as present for `add` and against the last-key guard only when sshd reads that file; otherwise it is listed as `ignored`.
- **Limitation**: other files are neither listed nor edited. A warning says so when `AuthorizedKeysFile` does not include `~/.ssh/authorized_keys` (sshd does not read the keys polyctl adds), names other files it includes (such as `/etc/ssh/keys/%u`), or is also set in a `Match` block, which may apply to the user instead. A note names an included file polyctl could not read (such files may be readable by root only), since it may set another `AuthorizedKeysFile`.
